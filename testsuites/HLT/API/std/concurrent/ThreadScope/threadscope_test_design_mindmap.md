## 阅读指引

本文档回答一个问题:**这 55 个用例是怎么被设计出来的?为什么恰好是这些用例?** 它按三个粒度展开:

- **第 0 层(方法论)**:设计任何一条并发 API 测试时走的五步推导链。它是"造用例的机器",后面两层的一切内容都是这条链跑一遍的产物。新增加用例时,应先把新用例放到这条链上找到位置,再动手写代码。
- **第 1 层(宏观分类)**:被测对象 threadScope/ThreadGroup 的生命周期模型,以及 55 个用例如何沿着生命周期分配到五个分支(A 进入 / B 执行 / C 消费 / D 失败传播 / E 泛型面)。读完这一层,你能对任意一个用例编号说出"它测的是生命周期上的哪一段"。
- **第 2 层(中观主轴)**:五个分支是静态的"在哪测",三条张力线是动态的"为什么必须成对地测"。很多用例看起来相似,其实是在同一张力的两侧卡边界——理解张力线之后,用例之间的关系就不再是孤立的列表,而是互相咬合的配对结构。
- **第 3 层(微观构造)**:落到单个用例文件上,一个合格的并发测试由哪五个要素构成。用 threadscope009 做完整解剖,并给出所有用例共用的工程纪律。

## 第 0 层 · 设计方法论:五步推导链

### 总述

这 55 个用例不是"想到什么写什么"的产物,而是由同一条推导链机械地产出的。这条链的价值在于:**任何一个没参与设计的人,拿到文档也能顺着链推出几乎同一组用例**;反过来,任何新增用例都应该能在这条链上找到自己的推导路径——如果找不到,说明它是拍脑袋写的,要么重复要么偏题。

### 第①步:提取语义承诺

通读官方文档(funcs.md 的 threadScope 专节、classes.md 的 ThreadGroup.launch/cancelAll/iterator 各专节、concurrent_package_overview.md、concurrent_samples 下 3 个 verify 样例),把**每一句可断言的话**登记为一条待测契约。判别标准是"动词级短语":一句话里包含一个可以验证真假的动作或结果,就是契约。

例如这几句都各是一条契约:

- "waits for every unconsumed task result" → 有用例验证:fn 返回后、scope 返回前,未消费的结果一定被等到(028);
- "Results are yielded as threads complete" → 有用例验证:产出顺序是完成序而非启动序(007/044);
- "The returned iterator's next() re-throws the exception or error of a consumed task if that task failed" → 有用例验证:next() 在取到失败结果时把它重抛出来(015/019)。

这一步的纪律是**不放过任何一句**,包括看起来像常识的句子。经验上,被跳过的"常识句"往往正是实现与文档分歧的地方。

### 第②步:还原生命周期阶段

并发 API 的契约大多不能孤立验证,必须挂在时间轴上。把 ThreadScope 的一次完整运行还原为三个阶段:

1. **执行期**——fn 体内调用 launch,任务在新线程上跑;此期间还可以调 cancelAll 发取消请求;
2. **消费期**——通过 for-in 或 iterator().next() 从结果队列读出任务产出;读是阻塞的,读到失败会重抛;
3. **收尾期**——fn 返回后,threadScope 先 waitForAll 消费完所有剩余结果,再返回;若 fn 本身抛异常,则改为 cancelAll + silentWaitForAll(静默清空队列)+ 重抛 fn 的异常。

把第①步登记的每条契约标注到它所属的阶段上。这一步最重要的认知转变是:**失败和取消是挂在这个时间轴上的"事件",不是瞬时生效的"全局开关"**。失败发生 ≠ 失败被看到;取消被请求 ≠ 取消被观察到。几乎所有并发语义的微妙之处都来自"事件发生时刻"与"事件被观测时刻"的间隙。

### 第③步:正/反命题配对

对每条契约问两个方向:"发生了会怎样"与"没发生会怎样",并让两个方向的用例成对出现。典型配对:

- 020 vs 030:失败**被消费**了(消费方已 try-catch 处理)→ 该失败不再传播到 scope 层;失败**未被消费**还留在队列里 → scope 收尾时会把它重抛。两个用例卡住"消费行为决定传播行为"这条语义的两侧。
- 004 vs 009:失败发生时 **fn 还在跑**(尚未返回)→ 取消请求会发给其余任务(004);失败发生时 **fn 已经返回**(scope 正在等待期)→ 兄弟任务不被打断、全部执行完毕(009)。
- 013/051(空组零迭代)与 029(200 个任务结果不丢不重)是一对规模上的两极。

配对的纪律是:**只写一个方向的用例等于没写**。只测"失败会传播"而不测"被消费的失败不传播",就无法防止实现把取消做成无差别全局开关——那种实现也能通过"失败会传播"的用例。

### 第④步:参数化维度扫描

对每条契约代入四个正交维度,机械地枚举出用例族:

- **类型面**:T 与 R 是两个独立泛型参数,各取代表值——T 取 String / Bool / Unit / 自定义 class / Option\<Int64\>(022/023/038/041),R 取 Unit / Int64 / 集合(008/042);
- **数量面**:任务数取 0(空组 013/051)、1(单任务 003)、3-4(典型多任务 009/044)、200(规模 029);
- **来源面**:失败来自任务体(003/009 等)、来自 fn 本身(016/025/026)、两者同时存在(054);
- **时序面**:失败发生在消费之前(015/019)、失败发生在消费进行中(043)、失败发生在消费全部完成之后(不可能再传播,由 020 反向钉住)。

维度扫描的产物必然有部分用例"看起来重复",这是正常的——它们仅在单一维度上不同,而这正是参数化测试的本意:当其中一例因类型/数量/时序而行为分化时,能立刻定位是哪个维度导致的。

### 第⑤步:确定性钉桩

并发用例最大的敌人是"碰巧通过"。每个用例必须把运气换成机制:

- **递增 sleep 钉完成序**:需要确定"谁先完成"时,给各任务安排严格递增的 sleep(如 20/50/80/110ms),使完成顺序由机制保证而非调度运气(007/022/044/009);
- **Atomic 跨闭包状态**:仓颉 lambda 捕获可变局部变量会编译失败,跨任务共享的观察变量一律用 AtomicBool/AtomicInt64(此为语言限制,也是本套用例统一风格);
- **墙钟上下界**:并发性用"总耗时远小于串行耗时之和"断言(027),等待语义用"总耗时不小于各任务 sleep 之和"断言(028),都留足余量(墙钟阈值取理论值与保护值之间,如 5s);
- **exit code 作预言机**:HLT 头部约定不做输出比对,所以每条断言收敛为 main 的返回值——所有可能抛异常的路径都 try-catch,把"是否抛、抛什么"编码成不同的非零 exit code,使失败可诊断;
- **退化行为可区分**:断言值的设计必须让"契约成立"和"契约缺失"产生**不同的 exit code**,而不是同为超时或同为崩溃(见第 3 层 009 解析)。

## 第 1 层 · 宏观:生命周期模型(思维导图主干)

### 模型本身

ThreadGroup 在实现上就是两样东西:**一个结果队列**(LinkedBlockingQueue,装 Ok(T)/Ex/Err 三种结果)+ **一个取消开关**(cancelled 标志 + futures 列表)。threadScope 则是给这个组合套上作用域的包装器,负责收尾。理解了这个"队列 + 开关"模型,下面的五个分支其实就是在问队列和开关各自的五组问题:

```
ThreadScope 测试全景(55 用例的宏观分配)
│
├─ A. 进入 scope —— 作用域与返回值契约(5 例:008 027 028 029 049)
│   这一组不关心失败与取消,只回答"scope 的进出是否干净":
│   · 008  fn 的返回值 R 被原样透传给 threadScope 的调用方(R=Int64 校验值正确)
│   · 027  多个任务真并发执行——4 个各 sleep 400ms 的任务,总耗时显著小于 1600ms,
│          证明 launch 不是串行执行的
│   · 028  fn 已经 return 了,但 scope 仍等待所有任务跑完才返回——
│          总耗时不小于最长任务的 sleep,证明 waitForAll 不受 fn 提前返回影响
│   · 029  规模压力:200 个任务全部 launch,消费时逐一校验值,结果不丢、不重、不错序
│   · 049  scope 嵌套:内层 scope 的 group 与外层互不干扰,
│          内层先正常收尾后外层继续,验证作用域边界
│
├─ B. 执行期 —— launch 与取消请求(10 例:001 006 011 021 033 034 045 046 047 048)
│   这一组回答"任务跑着的时候,launch 和 cancelAll 各自的行为":
│   · 001  launch 的返回类型面(返回 Unit,不返回 Future 句柄——句柄藏在 group 内部)
│   · 021  空组上调 cancelAll:无任务可取消,无副作用,scope 正常收尾
│   · 033  预取消:cancelAll 之后才 launch 的任务同样被置 pending cancellation
│          (cancelAll 的粘性语义),任务体内第一次检查就看到标志,立即退出
│   · 006  运行中取消:任务已跑起来再 cancelAll,协作式任务观察到标志后自愿退出

│          保持 false,证明取消不会误伤调用方

│   · 046  子任务内调 cancelAll:在任务体内部对自己的组发取消——不死锁、不崩,
│          语义按"钉现状"口径断言(此场景文档未明确承诺,不写超出现状的断言)
│   · 047  重复 cancelAll:幂等,第二次调用不再有新增效果
│   · 048  任务可无视取消:取消只是置标志,任务若不检查 hasPendingCancellation,
│          照常跑完并把 Ok(结果) 正常入队——取消是协作式的,不是强杀
│   · 011  launch 与 cancelAll 并发竞争(不持外部锁):不崩、不挂;
│          ConcurrentModificationException 若出现也可容忍——竞争窗口语义按现状钉住
│
├─ C. 消费期 —— 结果队列的读出协议(14 例:002 007 012 013 014 024 032 035 036 037 039 040 043 051)
│   这一组回答"结果怎么读、按什么序读、读完了是什么样":
│   · 002  最基础的 for-in 消费:3 个任务,for-in 逐个读出,值与数量都对

│   · 043  失败先入队、稍后才被消费:失败结果在队列里排队不影响先消费到的值,

│   一个失败从发生到被调用方看到,要穿过三层边界:
│   任务体(抛出)→ 队列(以 Ex/Err 形式排队)→ 消费方(iterator 重抛)→ scope 调用方(scope 重抛)。
│   这一组逐层验证异常不变形、不丢失、不提前:
│   · 003  单任务失败,异常经 queue → iterator → scope 完整传到调用方
│   · 015  iterator 层重抛:next() 取到 Ex 结果时按契约抛出(消费点观测)

│          重抛的是 fn 自己的异常,任务失败被静默清掉

    · 022  T=String:字符串结果经队列消费(顺带校验拼接与完成序)
    · 023  T=Bool:布尔结果消费
    · 038  T=自定义 class:引用类型作为结果类型,生命周期跨线程安全
    · 041  T=Option<Int64>:嵌套泛型作为结果类型,Some/None 都能走通
    · 042  R=集合类型:fn 把消费到的结果收集进 ArrayList 并返回
```

### 怎么用这个分配

- **按编号找位置**:任何一个用例先看它挂在 A-E 哪个分支,再读该分支的主题句,就知道它"在测生命周期上的哪一段、哪一组问题"。
- **检查分配均衡**:B(10)/C(14)/D(12)是最重的三个分支,与实现复杂度一致——执行期的取消矩阵、消费期的读出协议、失败的多层传播正是 ThreadGroup 实现里状态机最复杂的部分。A/E 轻是因为它们的契约简单清晰。
- **发现缺口**:新需求到来时先看五个分支各缺什么,而不是按用例编号顺延着写。

## 第 2 层 · 中观:三条贯穿性张力线(设计主轴)

第 1 层的五个分支是静态分类——它回答"测哪里"。但用例之间的**关系**不是分类能表达的:很多用例看起来相似,其实是同一条语义张力上**成对**出现的两个锚点,分别卡住边界的两侧。理解这三条张力线,55 个用例就从"一张清单"变成"一张互相咬合的网"。

### 张力一:失败何时打断谁?——失败是"排队的事件"还是"全局的开关"

这是整套设计里最核心的一条语义。实现(以及文档)的选择是:**失败是排进队列的一个事件,它的破坏力只在被消费的那一刻释放;唯一的全局反应是"消费到失败且 fn 已不在跑"时发一轮协作式取消请求**。沿这条张力,用例构成一个推理链:

1. **失败发生的瞬间,什么都不被打断**——009:任务1 抛异常后,其余 3 个兄弟任务照样全部执行到收尾处的 `fetchAdd`,原子计数到 4。若实现把失败做成全局急停,兄弟计数最多到 2,断言即破。
2. **破坏力的释放点之一:消费时**——015/019:next()/for-in 读到 Ex 结果的瞬间把它重抛,消费方在这个点被打断。
3. **破坏力的释放点之二:fn 失败时发取消请求**——004:fn 还在跑时失败被消费(或 fn 自己失败),scope 会向其余运行中的任务发取消请求;任务2 在几毫秒内观察到 `hasPendingCancellation`。
4. **但取消请求是协作式的、可无视的**——048:任务不检查标志就照常跑完,结果照常入队;033:预取消的任务第一条指令就能看到标志,但"看到"和"被杀死"是两回事;006/033/045/047 把取消请求在时间轴上的各时机展开成矩阵。
5. **回到传播侧:重抛的取舍**——010:多个失败排队时只重抛第一个,其余静默丢弃;054:fn 自己的失败优先于任何任务失败。这两个"丢弃"决定是文档明写的,用例钉死防止将来实现"好心"改成聚合全部失败。

这条张力的**反面**(失败如果做成全局开关会怎样)没有专门的"反面用例",因为 009 的断言本身就是反面命题的否证——这就是正/反配对在本套设计里的实际形态:一个用例的断言值同时排除退化语义。

### 张力二:消费了多少,决定 scope 怎么收尾——消费进度是收尾行为的开关

threadScope 的收尾不是单一行为,而是随"消费进度"和"fn 是否正常"变化的四种组合。这条张力组织了 D 分支的大部分用例:

| fn 结局 | 队列剩余 | 收尾行为 | 用例 |
|---|---|---|---|
| 正常返回 | 空(全消费) | 直接返回 | 002/007/012 等正常路径 |
| 正常返回 | 只有值 | 静默丢弃剩余值,正常返回 | 025/039 |
| 正常返回 | 有失败 | 等待期 iterator 把第一个失败重抛 | 030 |
| 抛异常 | 任意 | cancelAll + silentWaitForAll(清空全部) + 重抛 fn 的异常 | 016/026/055 |

特别值得指出的是 020 与 030 这对:**同一个失败,消费方已 try-catch 处理过 → 它就消失了,不再传播(020);没被消费、留在队列里 → scope 收尾时替你补上这一抛(030)**。这意味着消费方不能"消费了但吞掉失败还指望它再报一次",也不能"没消费就以为失败会无声消失"——两种期望都错,两个用例各钉住一侧。

### 张力三:同步承诺与并发现实的边界——哪些是确定性契约,哪些明确不管

并发 API 的文档必然只承诺一部分行为。设计上把全部行为空间切成三档,用例的写法随档位不同:

1. **确定性契约,写死断言**:并发执行(027,墙钟下界)、等待语义(005/028,墙钟上界)、完成序(007/044,机制钉序后精确断言)、结果完整性(029/032,逐值校验)。这一档的用例失败即 bug。
2. **未定义但钉住现状**:文档没有承诺、但需要记录实现当前行为的场景——并发竞争下不崩(011,断言"不崩不挂",对 CME 保留容忍)、子任务内 cancelAll 不死锁(046,只断言不死锁和基本收尾)。这一档的用例是"现状快照":实现将来若有意改变行为,用例应随文档更新一起改,而不是当作回归。
3. **文档明示不测**:三处文档定义为不支持/未定义的行为——ThreadGroup 逃逸出 scope、并发迭代同一 group、与裸 spawn 混用。**不写用例**,因为无断言可写:任何结果都符合"未定义"。这一档的存在本身要记录在文档里(见附录),防止后人"补全"它们。

## 第 3 层 · 微观:单用例的构造五要素(以 009 为例)

### 009 的完整解剖

threadscope009 验证的契约:**一个任务失败后,scope 在收尾等待期会把其余任务全部等完(而不是取消它们),失败本身只重抛一次**。源码结构是四个任务,各自 sleep 后对原子计数 `fetchAdd(1)`,其中第二个任务 sleep 完后抛 `Exception("boom")`;main 在 scope 外 catch 该异常并校验消息,再校验 `finishedCount == 4`。把它的构造拆成五个要素,每个要素对应一条可复用的通用规则:

| 要素 | 009 的实例 | 通用规则 |
|---|---|---|
| **契约** | 失败后 scope drain 全部任务,失败只重抛一次 | 一句话说清"谁在什么条件下应当怎样",写进头部 TEST INTENT;话说不成一句话,说明契约本身没想清 |
| **时序钉桩** | 四个任务 sleep 20/50/80/110ms,失败任务排在中间 | 递增 sleep 钉完成序;失败位置本身就是自变量(中间失败保证失败消费时仍有兄弟未收尾) |
| **观察点** | 每个任务收尾处对 AtomicInt64 `fetchAdd(1)` | 跨 lambda/任务共享的观察状态一律 Atomic——仓颉 lambda 捕获可变局部变量会编译失败,这不是风格选择而是语言强制 |
| **反事实** | 若失败即全局取消兄弟,finishedCount 只能到 2;断言 `==4` 使该退化实现必败 | 断言值必须能区分"契约成立"与"退化语义"——两个世界必须落到不同的 exit code,而不是同为超时或同为崩溃 |
| **预言机** | exit 0 = caughtMessage 正确 且 计数完整;exit 1 = 传播失败;exit 2 = 计数不完整 | HLT 头部约定不做输出比对,exit code 是唯一预言机;所有异常路径 try-catch 收敛为不同返回值,失败可诊断 |

### 通用工程纪律(全部 55 个用例共用)

1. **头部三行对回文档**:每个用例头部的 `TEST INTENT`(一句话意图)、`DOC REF`(引文档原句)、`EXPECT`(预期结果与 exit code)三行,分别对应第 0 层的契约、依据、预言机。审查任何一个用例时先读这三行,30 秒内判断它测什么、凭什么、怎么判。
2. **稳定性验收**:每个用例本地连续 5 次运行结果一致,再过 cangjie_test_framework 3 轮全绿,才算落地。并发用例一次通过不算数。
3. **未定义行为不写确定性断言**:对应张力三的第 2/3 档——现状快照用例(046/011)的断言只到"不崩、不挂、可收尾"为止,不写超出文档的行为断言;文档明示未定义的场景(组逃逸/并发迭代/spawn 混用)完全不写。
4. **CRLF 行尾**:与目录内既有用例(001-011)保持一致的仓库风格,cjc 对 `\r\r\n` 会报 unknown token,写文件时注意。
5. **失败的用例是信息**:修复历史中发现的 5 个编译不过/语义错误的旧用例(012/013/014/020/022),其错误本身就是发现——如 020 的 `result==5` 不可达暴露了"失败打断 for-in 消费"的真实语义,`finishedCount==3` 暴露了"失败任务自己不算执行完"。用例失败时先怀疑断言对语义的理解,再怀疑实现。

### 已覆盖

文档显式语义(funcs.md threadScope 专节、classes.md 三个方法专节、overview、3 个 verify 样例)的每一句可断言契约,除下述一条外,全部有对应用例。核对方法是:把文档逐句过一遍,每句找到对应用例编号,找 not found 的就是缺口——本次设计完成后缺口为零。

### 有意排除:Error 重抛路径

文档承诺 `Err(Error)` 也会被重抛(队列的 Result 枚举有 Err 分支,消费时 `throw e`)。但该路径在本环境下无法低成本验证:

- `Error` 类不可构造(构造器包级私有)、不可继承;
- 运行时可用的 Error 实际只有深递归触发的 StackOverflowError,单条用例因栈回溯捕获耗时约 9 秒,且行为受栈深度环境影响,不适合作为 HLT 稳定用例。

实现源码确认该路径与 Exception 路径共用同一套队列与重抛机制(`thread_group.cj` 的 `Result<T>` 枚举与 `nextResult` 的 match 分支),风险等级低,故有意排除并在此记录。若未来 Error 侧出现独立逻辑(如 Error 不走重抛),此处用例缺口需重新评估。

### 不设断言:三处未定义行为

- ThreadGroup 逃逸出 scope(文档:"Do not let the ThreadGroup\<T\> escape the scope");
- 并发迭代同一 group(类注释:"not safe for concurrent iteration");
- 与裸 spawn 混用。

三者文档均明示不支持,任何行为都符合规范,无断言可写。

### cancelAll 粘性语义的精确口径

cancelAll 之后才 launch 的任务同样会被置 pending cancellation——这是文档 "causes subsequently launched tasks to be cancelled as well" 的含义,实现上由 launch 内持锁检查 `cancelled` 标志并对新 future 补一次 cancel 保证(无竞态窗口),由 033 钉死。两个边界要分清:

1. **预取消不等于不执行**:spawn 照样发生,任务体第一条指令看到标志后如何处理是任务自己的事(033 里它选择立即退出;048 证明它也可以选择无视);
2. **被取消任务的成功值与正常值不可区分**:若预取消任务无视标志跑完,其 `Ok(结果)` 与正常任务的完全一样,消费方无从分辨——launch 返回 Unit,不提供取消指示。

这两个边界的含义:取消机制的可靠性最终落在"任务体自觉检查标志"上,调用方无法从外部强制。这是协作式取消的固有代价,文档以 "cooperative" 一词概括,本套用例用 033/048/006/048 把它的具体形态钉成可执行的断言。
